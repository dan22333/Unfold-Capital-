# AgentTorch Technology POC — trader archetypes

**This is a technology demo, not a trading signal.** It proves AgentTorch's
`Config`/`Runner`/`Substep` loop plus its LLM-archetype feature
(`Archetype`/`Behavior`) run end to end against real market data with a
local, open-weights model (Ollama). See `../agenttorch-explained.html` and
`../sim-alpha.html` for the actual business thesis this is a step toward.

## Checkpoint 2 (current): every trading day, no cherry-picking

Checkpoint 1 ran on one hand-picked ticker (AAPL) and one hand-picked event
(a famous Jan 2019 guidance cut) with archetypes whose conclusions were
scripted into their descriptions. That stacked two biases: the test case and
the model's assumptions were both chosen by the same person who already knew
which outcome would look validated. Checkpoint 2 fixes both:

1. **Disposition-based archetypes, not conclusion-coded.** Four personas —
   `momentum`, `contrarian`, `fundamentals` (new, modeled on how a real
   fundamental analyst discounts price moves without a visible cause), and
   `noise` — keep their real investing disposition but are explicitly told
   to use judgment about confidence given the actual data, not mechanically
   restate their label's conclusion. See `config/archetypes.py`.
2. **Every trading day is an example, not a hand-picked event.** AAPL, NVDA,
   and JPM (chosen for sector/volatility diversity, not a known outcome),
   every trading day in H1 2024 that has enough lookback history and
   forward-return runway — 372 examples total, mechanically generated by
   `src/market_context.generate_examples()`. No date is chosen because its
   outcome is already known.
3. **Reasoning capture.** Each archetype's full response (reasoning + the
   parsed stance) is kept, not just the number — see `outputs/examples.json`
   and the sampled reasoning in the dashboard.
4. **Richer context.** Archetypes see the trailing 15 trading days' daily
   returns, not a single summary percentage.

**Architecture note:** AgentTorch's population size is now the *number of
examples* (372), not the number of trader personas. Each example's
`aggregate_stance` becomes one row of an `[N, 1]` tensor; the learnable
`sensitivity` parameter is still calibrated via real backprop through one
vectorized `Runner.step()` call per training iteration — this is actually a
more faithful use of AgentTorch's tensor-population design than
Checkpoint 1's population-of-one.

**Result:** pooled across all 372 examples, the raw archetype signal (before
sensitivity scaling) shows essentially no correlation with what actually
happened (r ≈ 0.035). Broken down by ticker, AAPL alone shows a modest
positive correlation (+0.31, naively p=0.0004) while NVDA and JPM are
negative (−0.24, −0.20) — the sign flips by ticker, which is what washes the
pooled number to near zero.

**Update — that per-ticker correlation doesn't survive a proper
independence check.** The 124 "examples" per ticker aren't 124 independent
observations: each one's forward-return target window (20-40 trading days)
overlaps 95%+ with its neighbors', which inflates the naive p-values.
Resampled to genuinely non-overlapping windows, the honest n drops to 4-7
per ticker, nothing is statistically significant, and the correlation signs
become unstable across different sampling strides (JPM: −0.20 → +0.04 →
+0.69; NVDA: −0.24 → +0.17 → −0.46 depending on stride) — sign instability
that size is itself evidence of noise, not signal. A regime explanation
(momentum working better in trending markets) doesn't hold up either: NVDA
and JPM were the strongly-trending tickers in H1 2024 (trend_r 0.93, 0.88)
and AAPL was comparatively choppy (trend_r 0.37), but momentum's only
naively-positive correlation is on AAPL — backwards from what a trend
explanation would predict. See `src/analyze_significance.py` and
`outputs/significance_analysis.txt`.

Net: this is the honest result of a non-cherry-picked test, and the honest
result is "we don't have enough independent information in this window to
say anything yet" — not evidence for or against the mechanism. The
structural fix is a shorter forward horizon (more non-overlapping blocks
per unit of calendar time), which is nearly free to test since archetype
stances are cached and don't depend on horizon length — only `realized_target()`
needs to change, not any LLM calls.

## Architecture, stack, and runtime

**Pipeline** (each stage is a separate module, runnable standalone):

1. `src/pull_data.py` — one batched `yfinance` call for all tickers, written
   long-format to `data/raw/prices.csv`.
2. `src/market_context.py` — `generate_examples()` mechanically enumerates
   every (ticker, date) with enough lookback/forward-return runway (the
   bias fix); `recent_price_context()` builds the 15-day trailing-returns
   prompt context; `realized_target()` computes the 4wk/8wk forward return.
3. `config/archetypes.py` + `config/build_population.py` — 4 persona
   descriptions, compiled into a tiny real AgentTorch population
   (`config/trader_population/`: `persona.pickle` + `mapping.json`) via its
   actual `LoadPopulation`/`PromptManager` grouping mechanism.
4. `src/llm_backend.py` — `OllamaLLM(LLMBackend)`, a custom backend routing
   through local Ollama (AgentTorch's shipped `LangchainLLM` hardcodes
   OpenAI), capturing each call's full reasoning text alongside the parsed
   stance; includes one monkeypatch for a confirmed AgentTorch bug.
5. `config/model_config.yaml` + `src/substeps.py` — the actual AgentTorch
   model. `DecideStance` (Policy) builds `Archetype`/`Behavior` once, then
   loops all 372 examples calling `behavior.sample()` (cached per-example),
   producing an `[N, 1]` `aggregate_stance` tensor. `ComputePrediction`
   (Transition) multiplies it by the one learnable `SENSITIVITY` scalar,
   vectorized across the whole population in one `Runner.step()`.
6. `src/train.py` — builds the `[N, 1]` real-target tensor, runs Adam/MSE
   for 800 steps with genuine `torch.autograd` backprop through the real
   AgentTorch forward pass.
7. `src/evaluate.py` — correlation stats (overall/per-ticker/per-archetype),
   scatter data, a sampled-reasoning subset; writes `outputs/*.json` and the
   matplotlib PNGs; the published dashboard reads `dashboard_data.json`.

**Stack:** Python 3.13 venv (`poc/.venv`); `agent_torch==0.6.0`,
`torch==2.14.1`, `torch_geometric==2.8.0`; `langchain==0.3.27` pinned
(latest 1.4.x breaks AgentTorch's legacy memory/chains API — see rough
edges below); local `llama3.1:8b` via Ollama, GPU-accelerated on this
machine; `yfinance`/`pandas`/`numpy`/`matplotlib`. `requirements.txt` is a
full `pip freeze`, not just top-level packages, because of the version
landmines hit getting here.

**Datasets:** AAPL, NVDA, JPM daily adjusted close from `yfinance`, pulled
2023-11-15 → 2024-09-15 (buffer for lookback/forward-return), evaluated over
every trading day in 2024-01-02 → 2024-06-28 (372 examples, 124/ticker). Note
the existing `sim-alpha.html` doc already flags `yfinance` as prototyping-only,
not for rigorous backtests — fine for this purpose, not for the next one.

**What's working right now:** the full pipeline runs end to end via
`python run_poc.py`; all ~1,500 LLM calls (372 examples × 4 archetypes) are
cached by content hash to `cache/archetype_responses.json`, so re-running
analysis/training/dashboard code costs nothing further; the dashboard is
published and live.

**Runtime & scalability:** data-gathering is the only slow part — observed
roughly 1-1.5s/call on this GPU, so ~5s/example (4 calls), ~25-30 minutes
for the full 372-example run (done in 2-3 sittings only because of the tool
runtime's 10-minute cap, not the model). Calls are fully sequential, no
batching/concurrency yet. Training itself is not a bottleneck at all —
vectorized, cached data means 800 gradient steps run in a couple of
seconds. Scaling is roughly linear in `tickers × days × archetypes`: 10x
the current scope (e.g. 10 tickers × 2 years) would be several hours
sequential at this rate — real before that, we'd want either concurrent
Ollama requests (untested how many it handles well) or batching multiple
archetypes into one call, not a faster trained-parameter step.

**Alignment with AgentTorch:** this is a genuine use of the real engine, not
a mock or a bypass. `Config`/`Registry`/`Runner`/`Substep` genuinely drive
every training step; `Archetype`/`Behavior`/`LoadPopulation`/`PromptManager`
are AgentTorch's real LLM-archetype mechanism (one call per persona group,
broadcast via population) — here, the population dimension is repurposed to
be the 372 examples rather than millions of synthetic agents, which still
benefits from real vectorization (all 372 predictions in one `Runner.step()`
call) and is arguably a more interesting use of the tensor-population design
than a population-of-one. Known departures from "pure" AgentTorch idiom:
a plain global `nn.Parameter` instead of its config-driven `calibrate_*`
convention (not worth reverse-engineering for one parameter), a custom
`LLMBackend` subclass instead of the shipped OpenAI-only one (a documented,
supported extension point), and one bug patched in its own code.

**What the result says:** a 4-archetype LLM ensemble reacting *only* to
recent price action — no news, no fundamentals, no company-specific
information — shows no robust cross-sectional signal over an un-curated
sample. That's informative on its own: if there's real signal here, it
probably isn't going to come from "LLM applies a trading heuristic to a
price series," which is closer to what classical quant signals already do
and can do faster without an LLM. It's consistent with this repo's own
broader thesis (`../sim-alpha.html`) that the edge has to come from causal
reasoning about actual events and propagation, not price-pattern reactions.

## Roadmap — explicitly not built yet

Captured here so it doesn't get lost, and explicitly deferred until the
current per-archetype mechanism shows a real signal worth building on:

- **A senior/manager agent** that takes each archetype's view, combines and
  adjusts them with its own discretion (can weight, include, or exclude
  individual views) rather than a flat average.
- **A letter-grade output scale** (A = max overweight … E = max underweight,
  C = neutral) per company per day, in place of the continuous −1..1 stance.
- **Bet sizing and portfolio construction** — translating grades into
  position sizes and building an actual long/short portfolio (equal-weight
  or linearly weighted), then backtesting it.
- Per-ticker separate `sensitivity` parameters instead of one shared value.
- More tickers, a longer history, or a different evaluation period.

## Real rough edges hit building this

- `agent_torch==0.6.0`'s shipped `models/macro_economics` / `models/covid`
  examples import a stale, pre-refactor `AgentTorch.*` namespace that
  doesn't exist in the current package — don't use them as a reference.
- Its pip dependencies pull the *latest* LangChain (1.4.x), which removed
  the legacy `langchain.memory`/`langchain.chains` APIs it needs. Pinned to
  `langchain==0.3.27` (+ matching `langchain-openai==0.3.28`) —
  `requirements.txt` is a full freeze of the exact working set for exactly
  this reason.
- `PromptManager`'s `{variable}` extraction is a naive regex that doesn't
  understand Python format specs — use bare `{price}` placeholders and
  pre-format numeric values to strings before passing them as kwargs.
- **A real bug**: `LangchainMemoryHandler.save_memory` (in
  `agent_torch/core/llm/agent_memory.py`) unconditionally does
  `output["text"]`, but every `LLMBackend.prompt()` implementation —
  including the *shipped* `LangchainLLM` backend, not just our custom Ollama
  one — returns a plain list of strings. Unpatched, this throws on every
  call and `Behavior.sample()`'s retry loop silently swallows it, producing
  a NaN with no visible error. Patched with a one-line monkeypatch in
  `src/llm_backend.py`.
- A local model's stated reasoning and its final numeric answer aren't
  always coupled — one example in Checkpoint 2 has a contrarian archetype
  reasoning toward a reversal/rebound but outputting a bearish stance
  number. Worth knowing when interpreting results; see `outputs/examples.json`.

## Setup

```bash
python -m venv .venv
./.venv/Scripts/python.exe -m pip install -r requirements.txt   # Windows
# or: source .venv/bin/activate && pip install -r requirements.txt

ollama pull llama3.1:8b   # or llama3.2:3b if that's too slow locally
```

## Run

```bash
python src/stage0_verify_ollama.py    # confirm the local model responds at all
python src/market_context.py          # sanity-check example generation
python run_poc.py                     # full pipeline: data -> 372 examples -> train -> evaluate
python src/analyze_significance.py    # honest, overlap-corrected significance + regime context
```

The data-gathering step (~1,500 LLM calls) is the slow part and is safe to
interrupt and resume — results are cached to `cache/archetype_responses.json`
by content hash, so a re-run only computes what's missing.

Outputs land in `outputs/`: `results.json`, `dashboard_data.json`,
`examples.json` (full per-example detail including reasoning text),
`loss_curve.png`, `predicted_vs_actual.png`.
