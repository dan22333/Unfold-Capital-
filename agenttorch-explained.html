Part 0 · Orientation

What this thing even is

Before any code: one honest paragraph on what AgentTorch is, who made it, and the single mental model that makes everything else click.

▸ Definition — Agent-based model (ABM)

An agent-based model is a simulation where you give many individual "agents" simple rules ("if a sick neighbour visits, I might catch it"; "if my wage falls, I spend less"), let them interact over time, and watch what emerges at the population level — an epidemic curve, a recession, a market panic. The behaviour of the whole is never written down directly; it emerges from millions of small local rules.

▸ Definition — Large Population Model (LPM)

AgentTorch's authors brand their flavour of ABM as a Large Population Model. The readme's own line: "While LLMs build digital humans, LPMs build digital societies." The pitch is that an LLM captures one person's reasoning, but an LPM captures the ripple effects of millions of interacting decisions — the collective-scale dynamics an LLM alone can't represent.

AgentTorch is an open-source Python framework (AGPL-3.0, © Ayush Chopra, MIT Media Lab) for building these LPMs. Its four stated design principles — verbatim from the readme, paraphrased in plain English:

  • 1Scalability. Simulate very large populations (their headline demo is 8.4 million synthetic New Yorkers) in seconds, by running everything as batched tensor math on a GPU.
  • 2Differentiability. You can take the derivative through the whole simulation — even though it's full of random events and if-then rules — so you can tune it with gradient descent, the same way a neural network is trained.
  • 3Composition. The simulation can be wired together with neural nets. An LLM can supply agent behaviour; a small neural net can supply the simulation's parameters. This is the hook we care about.
  • 4Generalization. Same machinery is meant to run humans-in-cities, cells-in-tissue, or avatars-in-games.
The one mental model to hold

AgentTorch is PyTorch, but the "network" is a world.

A neural net is a stack of differentiable layers; you press forward(), get an output, compute a loss, press backward(), and the gradients tell you how to nudge every weight. AgentTorch makes the rules of a world — contagion, spending, predation — into those differentiable layers. Press forward() and the world steps through time. Compute a loss on the outcome (e.g. "simulated cases minus real cases"). Press backward() and the gradients tell you how to nudge every rule-parameter (transmission rate, mortality, spending propensity). That single idea is the whole framework. Everything below is plumbing that keeps this true even where a normal simulation would break the gradient.

Part 1 · The evidence

What they actually built & showed

The repo ships three worked models. Here is what each one demonstrates — the claim it's proof of — and how it does it. This is the "is the idea real?" evidence, so I'm careful to separate what the code plainly does from what the associated papers claim.

1.1COVID — the flagship: 8.4M agents, LLM behaviour, gradient calibration

File tour: models/covid/ — model_card.md, substeps/new_transmission/, calibration/calibnn.py.

What it shows. That you can stand up a full city (8.4M synthetic NYC residents, ages + a mobility contact network), run an SEIRM disease process (Susceptible → Exposed → Infected → Recovered → Mortality), let agents make an adaptive behavioural choice ("will I isolate today?") that can be driven by an LLM, and then calibrate the disease parameters (like R0, initialised to 4.75 in the card) to real case data by gradient descent — the differentiability principle, made concrete on a population the size of a real city.

How it works, mechanically. Each simulated day runs two substeps: Transmission then Disease Progression. In Transmission, the contact network decides who is exposed to whom (message passing — §2.2), the per-agent isolation decision damps their contacts, a random draw decides who actually gets infected, and stages advance. Because every one of those steps is written in a differentiable way, a loss on "daily infected vs. real data" flows all the way back to the transmission rate.

▸ Honesty note

The code plainly implements the population, the SEIRM dynamics, the LLM-isolation hook, and the calibration machinery (learnable R0/mortality, an Adam loop, a CalibNN net with hard parameter bounds). The stronger claim — "it reproduced real NYC COVID waves and beat baselines" — belongs to the associated papers (Chopra et al., differentiable agent-based epidemiology), which I'm citing from memory, not re-verifying here. Treat "it fit real data well" as my recollection until you read the paper.

1.2Macro-economics — LLM consumers inside a differentiable economy

File tour: models/macro_economics/ — simulator.py, substeps/{earning,consumption,labor_market,financial_market}, calibnn.py.

What it shows. A tiny economy where agents earn and spend, a labour market updates unemployment, and a financial market ("FED") updates interest rates and taxes — with the agents' work-and-consumption decisions optionally driven by an LLM. The differentiable payoff is explicit in the source: after running an episode it computes loss = unemployment_rate.sum(), calls loss.backward(), prints p.grad for every parameter, and steps an Adam optimizer (simulator.py lines ~102–115). So the demo is "differentiate the unemployment rate with respect to the economy's parameters and optimize."

Why it matters for you. This is the closest shipped analogue to a market: heterogeneous agents, a price/rate-setting market layer, LLM-driven demand, and a gradient from a macro outcome back to behavioural parameters. It's the template you'd mutate.

1.3Predator–prey — the pure "scale & correctness" demo

File tour: models/predator_prey/ — vmap_simulation.py, substeps/.

What it shows. No LLM. It's the classic ecology ABM — predators, prey, and regrowing grass on a grid, each with an energy level; things eat, move, reproduce, and die. Its job is to prove the vectorized runner reproduces textbook predator–prey population oscillations while scaling, and to serve as the framework's teaching example (there's a whole tutorial on "vectorizing" it). It's your reference for "how do I write a model that isn't disease" and how the observe→act→progress substep pattern feels on a fresh domain.

▸ What is not in this repo

The readme advertises "cells in anatomical worlds" (neural cellular automata) and other domains, but the shipped models/ folder contains only covid, macro_economics, predator_prey. Some example scripts reference boids/movement models too. If a demo isn't in models/ or examples/, treat it as a paper/website claim, not runnable code you have.

Part 2 · The machinery

How a run physically works

Now the gears. Four things to understand in order: (a) the world is just tensors, (b) time advances by a three-phase loop, (c) agents interact by message passing, (d) the LLM plugs into exactly one phase.

2.1The world is a nested dictionary of tensors

There is no Agent object per person. That's the key surprise. The entire population lives in one big state dict of PyTorch tensors. Agent number 4,000,000 is simply row 4,000,000 of each tensor:

state = {
  "agents": {
     "citizens": {
        "disease_stage": tensor(shape=[8_400_000, 1]),  # 0=S,1=E,2=I,3=R,4=M
        "age":           tensor(shape=[8_400_000, 1]),
        "infected_time": tensor(shape=[8_400_000, 1]),
     }
  },
  "environment": { "daily_infected": tensor(...), "R2": tensor(...) },
  "network":     { # the contact graph: an edge list (who meets whom) },
}
▸ Why this is the whole scaling trick

Updating 8.4M agents is not a Python loop over 8.4M people (that would take minutes per step). It's one tensor operation — new_stage = stage + newly_infected — that the GPU applies to all 8.4M rows at once, in parallel. "Millions of agents" = "tall tensors + one vectorized op." That is the entire performance story; the rest of the framework is about keeping that world differentiable.

2.2Time advances by a three-phase substep loop

The Runner (itself a PyTorch nn.Module) walks time. One simulation "tick" (e.g. a day) is broken into substeps (Transmission, Progression, …) that you list in a YAML config. Each substep runs three phases, executed by the Controller (core/controller.py):

1 · Observe
SubstepObservation — slice out only the state tensors this rule needs (e.g. each agent's stage & age).
2 · Act / Policy
SubstepAction — decide each agent's action (e.g. "isolate: yes/no"). The LLM plugs in here.
3 · Progress / Transition
SubstepTransition — apply the deterministic dynamics: actions + network → the next state.
for t in range(num_steps):            # each day
    for substep in substeps:          # Transmission, then Progression
        obs   = controller.observe(state)          # phase 1
        act   = controller.act(state, obs)         # phase 2  ← LLM here
        state = controller.progress(state, act)    # phase 3  → next state
        trajectory.append(snapshot(state))         # recorded history you analyse later

That's it — the "algorithm of a run" is this triple-nested loop (timesteps × substeps × three phases), where every phase is a batched tensor op over the whole population. The recorded trajectory is what you compute losses and statistics on afterwards.

Part 2.3 · The part you asked about

How message passing actually works

"Agent-to-agent interaction via graph message passing" is the phrase you flagged. Here is the literal mechanism, with a worked 3-agent example. This is also the single most important section for your fund idea, because a supply chain is a message-passing graph.

▸ Definition — a graph, an edge list, message passing

A graph is dots (nodes) joined by lines (edges). Here each node = one agent; each edge = "these two are in contact." The graph is stored as an edge list: a 2-row tensor where column k says "edge k goes from node edge[0,k] to node edge[1,k]." Message passing is a 3-step recipe that lets every node update itself using its neighbours — and crucially it runs as one vectorized op over all edges at once, not a loop over nodes.

AgentTorch inherits this from PyTorch Geometric's MessagePassing class. The COVID transmission substep (new_transmission/transition.py) subclasses it and calls self.propagate(edge_index, x, ...). propagate orchestrates exactly three steps:

① message()
For every edge j→i at once, compute the "message" flowing from source neighbour j to target i. In COVID this is the infection pressure agent j puts on agent i: a product of i's susceptibility, j's infectiousness, the edge's contact weight, and a time-since-infection factor. Non-infected j contribute zero. This is the method message() in the file (it calls _lam(...)).
② aggregate()
For each target node i, sum all incoming messages. The class was constructed with aggr="add", so node i ends up with its total infection pressure = sum over all its infected contacts. PyG does this sum in one scattered tensor op.
③ update()
Turn the aggregated pressure into the node's new value. Here it's essentially the identity — the summed pressure is the per-agent transmission intensity, called new_transmission.
▸ Worked example — 3 agents, one infected

Agent i (susceptible) has two contacts: j₁ (infected) and j₂ (healthy). Edge list has two columns pointing at i.

① message: from j₁ → i, pressure = R · susci · infectj₁ · weight · γ ≈ 0.30. From j₂ → i, j₂ isn't infected so pressure = 0.
② aggregate: total pressure on i = 0.30 + 0 = 0.30.
③ update → then the substep converts pressure to a probability:

P(i stays uninfected) = e−0.30 = 0.741  ⟹  P(infected) = 1 − 0.741 = 0.259exp-dose

Then a random draw with probability 0.259 decides whether i actually flips to Exposed today (that draw is the StraightThroughBernoulli of §3 — the thing that keeps the gradient alive). Multiply by "am I isolating?" (the LLM's output) to damp it.

Direct mapping to your fund

A supply chain is this exact object.

Swap the labels: node = a firm; edge = "firm A supplies / is a customer of / competes with firm B" (with an edge weight = strength of the link); message = an economic shock (an input-cost spike, a demand cut, an earnings surprise) propagating along that edge; aggregate = a firm's total exposure summed over all its links; multi-hop = run the message pass twice and the shock reaches suppliers-of-suppliers. The COVID transmission code is, structurally, a shock-propagation engine. That's why AgentTorch is relevant to you at all — not the epidemiology, the graph diffusion machinery.

Part 2.4 · The LLM's real job

What the LLM does — and why it's allowed near probabilities

Your sharpest question: "LLMs are bad at predicting probabilities, so why let them decide probability?" The honest answer is that in a well-built AgentTorch model they don't. Let's see exactly what the LLM returns and where it sits.

2.4.1The archetype trick: tens of calls, not millions

The naïve fear is 8.4M GPT calls per step. That is not what happens (core/llm/behavior.py, prompt_manager.py):

  • 1Your prompt is a template with slots: "You are {age} in {region}. Cases are {change} this week. Will you isolate today? Answer 0–1."
  • 2The PromptManager takes the Cartesian product of the slot categories (itertools.product). 7 ages × 5 regions = 35 distinct groups → 35 prompts → 35 LLM calls. Not 8.4M.
  • 3Calls fire in parallel (a thread pool over the group prompts; backends include DSPy/OpenAI, and a MockLLM for free local dev).
  • 4Each answer is parsed to a number (value = float(text)), then broadcast back onto every agent in that group via a boolean mask tensor — one scatter op puts the 35 answers onto all 8.4M rows.
  • 5n_arch = how many independent "persona samples" you draw per group; their numbers are averaged, giving a distribution rather than one point.
▸ Definition — archetype

An archetype is a behavioural persona shared by everyone with the same slot values. It's the compression that makes LLM-in-the-loop affordable: reason once per type of person, broadcast to all instances. This is the "adaptive behaviour / Lucas-critique" idea from your other doc, in code.

2.4.2Where the LLM sits — and where it does not

Trace the COVID isolation action (new_transmission/action.py): the LLM's number becomes will_isolate, a per-agent tensor, returned as the action. In the transition it multiplies contact intensity: exposed = bernoulli(prob) · (1 − will_isolate). So the LLM sets a behavioural propensity that modulates a mechanism whose hard numbers come from elsewhere.

▸ Two facts that resolve your objection

(a) The LLM is outside the gradient. Its text output is turned into a plain float — that float() cast severs any connection to the LLM's weights. Gradients flow through the mechanistic parameters (transmission rate, mortality), not back into the language model. The LLM is a behaviour oracle, not a trained layer.

(b) The LLM supplies direction & structure; the data supplies magnitude. You should not ask the LLM "what is the probability of infection" (it is badly calibrated at that). You ask it the thing it's good at: "holding all else equal, does this persona isolate MORE or LESS when cases jump?" — a qualitative, conditional behavioural response. The actual numeric strength (how much a unit of "isolation propensity" reduces transmission) is a learnable parameter calibrated to real data by gradient descent. The LLM never gets to set a probability that matters quantitatively; it sets the shape of the response and lets the differentiable sim fit the size.

The reusable principle for your fund

Let the LLM build the graph and pick the sign; let gradient descent set the coefficients.

Don't ask an LLM "what's the probability GM's stock drops 3%." Ask it the two things it's genuinely good at: (1) structure — "read this 10-K; which suppliers does firm X depend on, for which input?" (graph construction) — and (2) direction — "if that input's cost spikes, does a thin-margin downstream firm cut output or raise price?" Then a differentiable propagation model, calibrated to historical returns, decides the magnitudes. This is precisely the split your sim-alpha.html verdict already argues for; AgentTorch is one concrete way to implement the second half.

Part 3 · The magic trick, from scratch

How a coin-flip carries a gradient

This is the section you said you don't get at all. We'll build it from the very bottom: what a gradient is, why simulations normally destroy it, and the three specific tricks the code uses to save it.

▸ Plain-English on-ramp — what is a gradient?

A gradient (derivative) answers one question: "if I nudge this input up a tiny bit, how much does the output change, and in which direction?" If output = 3·x, the gradient is 3 ("each unit of x adds 3 to output"). PyTorch computes these automatically for any chain of smooth operations — that's autograd / backpropagation. Training = repeatedly reading the gradient and stepping the inputs the direction that lowers a "loss." No gradient ⟹ no gradient-descent training.

▸ The problem — simulations are full of gradient-killers

Two operations appear everywhere in a simulation and both have a zero-or-undefined derivative, which snaps the chain:

(1) A random 0/1 event. "Did agent i get infected?" is a coin flip — torch.bernoulli(p) outputs exactly 0 or 1. Nudge p a hair and the output usually doesn't move at all (still 0), then suddenly jumps. Derivative is 0 almost everywhere. So the gradient can't travel from "number infected" back to the transmission rate p depends on.

(2) A comparison / if-statement. "Is energy > 0?" → (a > b) is a step: flat 0, then flat 1. Derivative 0 everywhere except an infinite spike at the edge. Same breakage.

If you leave these as-is, loss.backward() returns zeros and calibration is impossible. AgentTorch's whole "differentiability" claim rests on replacing these with look-alikes that have a usable gradient.

3.1Trick 1 — the Straight-Through estimator (the Bernoulli)

Here is the actual code from core/distributions/distributions.py — it's tiny:

class StraightThroughBernoulli(torch.autograd.Function):
    @staticmethod
    def forward(ctx, p):
        result = torch.bernoulli(p)      # a REAL coin flip → hard 0 or 1
        ctx.save_for_backward(result, p)
        return result
    @staticmethod
    def backward(ctx, grad_output):
        result, p = ctx.saved_tensors
        return grad_output * torch.ones(result.shape)   # pretend d(sample)/d(p) = 1
▸ What "straight-through" means, unpacked

A PyTorch autograd.Function lets you write the forward pass and the backward pass by hand, independently. Here they deliberately lie to each other, productively:

Forward: do the honest thing — flip a real coin, output a hard 0 or 1. The simulation stays realistic (an agent is either infected or not; no fractional people).

Backward: the true derivative of a coin flip is 0/undefined, which would kill training. So instead they pass the incoming gradient straight through unchanged (multiply by 1), as if the output had simply been p itself (whose derivative w.r.t. p is 1). The gradient "walks through" the coin flip on a pretend-smooth bridge.

▸ Worked example — why this lets you calibrate R

Suppose transmission rate R feeds probability p = 0.259 (from §2.3), and the coin flip gives 0 (i infected: no). Total infections today is some sum of these flips; say loss = (infections − real_data)².

Forward uses the hard 0 — infections is an honest integer.
Backward: the straight-through rule says "treat that flip as if it were p," so ∂infections/∂p ≈ 1 per agent, and the chain continues: ∂loss/∂R = ∂loss/∂infections · ∂infections/∂p · ∂p/∂R. Now R has a gradient, so Adam can nudge R to make simulated infections match reality. Without the trick, ∂infections/∂p = 0 and R would never move. That's the entire point.

Caveat Straight-through is biased — it's an approximation, not the true gradient. The repo also ships fancier unbiased estimators (Bernoulli, Binomial, Geometric, Categorical) whose backward uses "stochastic-triple" weights like 1/p and 1/(1−p). Straight-through is the cheap default; the others trade cost for less bias.

3.2Trick 2 — Gumbel-softmax (for "pick one of several options")

When the choice is categorical (buy A vs B vs C, not just yes/no), the same problem appears and the fix is Gumbel-softmax (helpers/soft.py, discrete_sample → torch.nn.functional.gumbel_softmax(logits, tau=0.1, hard=True)).

▸ How it works, plainly

To sample a category differentiably: add a specific kind of random noise (Gumbel noise) to the option scores, then take a softmax (a smooth, differentiable "soft argmax") with a temperature τ. Low τ (here 0.1) makes the softmax output almost a hard one-hot pick — so the forward pass looks like a real choice — while the softmax's smoothness gives a real gradient on the backward pass. hard=True adds a straight-through step so the forward value is exactly one-hot but the gradient still flows. It's the §3.1 idea generalised from a coin to a die.

3.3Trick 3 — soft logic (the hard + soft − soft.detach() line)

This is the one-liner you quoted. It differentiably fakes comparisons and boolean logic (helpers/soft.py). Take compare(a,b) ≈ "is a > b?":

hard = (a > b).float()          # exact step: 0.0 or 1.0
soft = torch.sigmoid(k*(a - b)) # smooth S-curve version of the same question
result = hard + soft - soft.detach()
▸ Why that line is genius (and what .detach() does)

.detach() means "keep this number's value but cut it out of gradient bookkeeping — treat it as a frozen constant." Now read the line twice:

Forward (values): soft − soft.detach() = soft − (same number) = 0. So result = hard, exactly. The simulation sees a clean 0 or 1. No fuzziness leaks into the dynamics.

Backward (gradients): hard has gradient 0 (it's a step); soft.detach() has gradient 0 (frozen). The only term left with a live gradient is soft — the sigmoid — whose derivative is a nice smooth bump. So the gradient of result equals the gradient of the soft version. You get a hard value forward and a smooth gradient backward, from one line. The same pattern builds min, max, and, or, not.

▸ The section in one sentence

Every gradient-killing operation (random events, comparisons, choices) is swapped for a twin that behaves exactly like the real thing on the way forward but hands back a smooth, usable gradient on the way back — so the whole simulation becomes one long differentiable function you can train like a neural net.

Part 4 · Payoff

Calibration & sensitivity, made literal

Now that the sim is differentiable, two things you asked about fall out almost for free. They're the same machine used two ways.

4.1How a parameter becomes trainable

In the YAML you mark an argument learnable. If calibration is on, the substep's constructor does (core/substep.py):

setattr(self, f"calibrate_{key}", torch.tensor(value, requires_grad=True))

requires_grad=True is the switch that tells autograd "track this; I'll want ∂loss/∂(this) later." In COVID, the weekly transmission rate R2 becomes such a tensor and is used as R = (calibrate_R2 · week_onehot).sum().

4.2Calibration = gradient descent to fit real data

▸ Definition — calibration

Calibration = finding the parameter values that make the simulation reproduce reality. The old way is black-box search: guess parameters, run the whole sim, measure error, guess again — thousands of full re-runs, because you have no idea which way to move. The differentiable way: one run tells you, via the gradient, exactly which direction lowers the error for every parameter simultaneously. It becomes ordinary neural-net training.

The macro model's real loop (macro_economics/simulator.py, condensed):

optimizer = optim.Adam(runner.parameters(), lr=...)   # the calibrate_* tensors
runner.step(num_steps)                                 # run the whole economy
unemployment = runner.state_trajectory[-1][-1]["environment"]["U"]
loss = unemployment.sum()          # (or MSE vs. real unemployment series)
loss.backward()                    # backprop THROUGH the whole simulation
optimizer.step()                   # nudge every parameter down its gradient

Repeat over episodes and the parameters converge to values that reproduce the target series. Same pattern in COVID with case data.

4.3Sensitivity = you literally read .grad

▸ Definition — sensitivity

Sensitivity = "how much does the outcome I care about move when I change this one knob?" Formally the derivative ∂(outcome)/∂(parameter). After a single backward(), PyTorch has stored exactly this in each parameter's .grad field. So:

total_infections = trajectory_infections.sum()
total_infections.backward()
print(runner...calibrate_R2.grad)   # = ∂(total infections)/∂R2
                                    # "each +1 unit of R2 ⟹ +N infections"
▸ Why this is a superpower vs. the normal way

The brute-force way to get sensitivities is finite differences: bump R2, re-run the whole 8.4M-agent sim, see how infections changed; then bump mortality, re-run again; … one full re-run per parameter. With 50 parameters that's 50 city-scale simulations.

Autograd gives you all 50 sensitivities from a single backward pass — because backprop propagates the derivative to every parameter at once. Rank parameters by |grad| and you instantly know which levers actually move the outcome and which are noise. That "full sensitivity ranking, basically free" is the thing that makes differentiable simulation more than a gimmick.

4.4CalibNN — a neural net that outputs the parameters

covid/calibration/calibnn.py and the macro calibnn.py take this one step further. Instead of a fixed learnable number for R, a small neural net reads features (mobility, weather, week-of-year) and predicts the parameters, squashed into sensible bounds (the file hard-codes MIN_VAL_PARAMS/MAX_VAL_PARAMS, e.g. R0 ∈ [1.4, 6.0]).

▸ And P3O — for the parts that truly can't be made smooth

optim/p3o.py is a policy-gradient optimizer (the REINFORCE family — the estimator used in reinforcement learning when you can't differentiate a discrete choice). It's used for genuinely non-differentiable knobs, like which prompt wording to show the LLM. Instead of a true gradient, it nudges choices toward whatever scored better, using the log-probability of the choice weighted by the reward. Think of it as the fallback for the handful of decisions the §3 tricks can't smooth.

Part 5 · The "what if" question

Counterfactuals — why a simulator can answer them

You saw questions like "what would have happened if…?" Here's why a mechanistic simulator can answer those, where a plain predictive model can't — and the honest limit.

▸ Definition — counterfactual

A counterfactual is a question about a world that didn't happen: "what if we'd locked down a week earlier?", "what if oil had spiked 30%?" You can't look it up in data because it never occurred.

▸ Why regression/ML struggles

A model trained to predict from correlations only knows the world as it was. Ask it about an intervention outside its data and it extrapolates blindly — it learned "these move together," not "this causes that." (This is the Lucas critique: relationships break when you change the policy.)

▸ Why a simulator can

An ABM encodes the mechanism: change the input (lockdown date, oil price, an edge weight), press play, and the consequences propagate through the rules. You get a full alternate trajectory. You can even optimize the intervention by gradient descent — "find the lockdown timing that minimizes deaths subject to cost" — because the sim is differentiable.

Mechanically, a counterfactual is trivial to run: change a parameter tensor or an intervention flag in the config and call runner.step() again; diff the two trajectories. That's the entire "what if" engine.

▸ The honest limit — say this out loud in any pitch

A counterfactual is only as trustworthy as the mechanism. If your rules or your calibrated coefficients are wrong, the alternate world is confident fiction. Simulators don't escape the "garbage-in" problem; they relocate it from "did I fit the past" to "is my mechanism right." For markets specifically, mechanism is exactly what's contested — so counterfactual market claims are a hypothesis to be validated forward, never a proof. (This is consistent with the tier-2/tier-3 "backtestability spectrum" already in your sim-alpha.html.)

▸ Good fit
  • ✓Slow multi-hop diffusion: a supplier's guidance cut rippling to customers & their customers over weeks.
  • ✓Input-cost / commodity shocks propagating down value chains.
  • ✓Scenario stress tests: "oil +30% — who's exposed two hops out that the market hasn't repriced?"
  • ✓Low-attention names where the link is non-obvious, so diffusion is slow (your thesis's core).
▸ Bad fit
  • ✗High-frequency / microstructure — wrong timescale entirely.
  • ✗Efficient large-cap next-day — repriced before your ripple arrives.
  • ✗Anything where you'd need the LLM to output a calibrated probability directly (§2.4).
  • ✗Regime bets with no historical analog — that's the tier-3 "gambling" zone from your other doc.

6.3The simplest experiment that would actually tell you something

▸ A leakage-proof mini-POC (fits your 4–8 week horizon)
  1. Pick one clean shock channel. E.g. supplier issues a downward guidance revision on date D.
  2. Build the graph from pre-D information only. Use an open-weight LLM with a fixed knowledge cutoff before D to read pre-D filings and extract "firm X depends on supplier S for input I." This is the leakage guardrail — the model literally cannot know the future.
  3. Propagate. One or two message-passing hops with a single learnable decay coefficient. Output: predicted sign & size of each linked firm's 4- and 8-week forward return.
  4. Calibrate the decay on a disjoint, earlier set of shocks; test on held-out later ones.
  5. Compare against three baselines: (a) the market itself, (b) a plain-LLM sentiment score on the same news, (c) the naïve Cohen–Frazzini customer→supplier trade.
  6. Metric: out-of-sample hit-rate / information ratio on the linked basket, with the LLM cutoff strictly before every event.
▸ The unlock — you don't need the agent machinery for the POC

For a first spillover POC you can skip the millions-of-LLM-agents part entirely. The reusable 20% is: a differentiable message-passing graph + gradient calibration. That's a few hundred lines of plain PyTorch (or AgentTorch's MessagePassing substep + the StraightThrough/soft ops). The LLM's only job in v1 is graph construction + sign. Bringing in behavioural archetype-agents (à la macro model) is a v2 upgrade, not a prerequisite. Right-size the tool to the question.

6.4Is "what they did" already proof?

Partly. It's proof of capability — that graph-diffusion + differentiable calibration + LLM-supplied structure scales and can fit real data in a hard domain (epidemics, macro). It is not proof of market alpha: markets are adversarial and near-efficient in a way epidemics aren't, and the counterfactual limit (§5) bites hardest exactly here. So: strong existence proof for the architecture; the edge is yours to demonstrate with the POC above. That distinction is the honest thing to tell an investor.

Part 7 · Beyond the demos

What else can be done & how to extend it

Concrete extension paths, cheapest-and-most-relevant first.

  • 1Multi-edge-type graph (a real GNN). Give each link type (supplier, competitor, co-input, shared-analyst) its own learnable propagation weight. Calibrate all of them jointly; read sensitivities to learn which link type actually carries slow-diffusing information. This is the direct generalisation of the single-R COVID transmission.
  • 2CalibNN for firms. A small net mapping firm features (size, margin, leverage, liquidity) → its response coefficient, instead of one global decay. Same trick COVID uses for R; lets the response depend on who the firm is.
  • 3Counterfactual/scenario engine as a product. Even if alpha is uncertain, a differentiable "who's exposed if X shocks" tool is a legitimate risk deliverable — and you can gradient-optimize hedges against a scenario.
  • 4Behavioural archetype layer (v2). Only once the graph edge works: add LLM-driven agent responses (management cutting capex, competitors repricing) the way the macro model adds consumers — to capture second-order behaviour the static graph misses.
  • 5Swap the LLM backend to open-weights. The backend is abstracted (core/llm/backend.py: an abstract LLMBackend, plus DSPy and a MockLLM). Writing a Claude/open-weight backend is implementing one prompt() method — and open weights give you the auditable-cutoff property your leakage story needs.
▸ Practical friction to expect

The two shipped trainer.py files have hard-coded absolute paths (/Users/shashankkumar/…) and a stale import (from AgentTorch.helpers, the old package name — it's now agent_torch). Treat them as reference. The clean entry points are agent_torch/examples/*.py and docs/tutorials/. Start with MockLLM and a small population to watch the loop turn before spending a cent on API calls.
